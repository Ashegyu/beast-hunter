# Alpha 0.84 — preparation, bag retention and staged loading

## User-visible changes

- Put a compact preparation panel at the top of the hunt map and result report. It shows actual inventory capacity, remaining training points and remaining skill-rank points, and opens equipment/growth/skills directly. Time-out copy explains equipment and area-skill preparation. Result shortcuts settle the run through the existing return-to-camp transition; they do not spend points, equip items or start another hunt automatically. The existing result-skill action and milestone focus are reused.
- Increase inventory storage **24 → 48**. Keep **24 visible slots and 24 detail panels** and page the view. Filtering/sorting returns to the first page; opening a specific item finds its page. Actions resolve through the visible item identity, and bulk selection/protection stay keyed by item ID. Show remaining room/full-bag policy and the actual number of automatic conversions on results.
- Use one small inventory-rules module for the bound shared by loot storage and crafting. Existing native saves (version 8), old 24-item profiles and backup envelopes remain readable. Reserved ground loot stays capped at 24, with existing once-only recovery and conversion rules. Equipped, favorited and saved-build items retain protection. Drop tables, rarity pity, item power, skills and 60-second limits are unchanged.
- Open the camp after three preview images. Hunt-map preparation or the first launch loads the remaining shared combat set plus selected region. Each shared bundle owns a private image map until all images and metadata validate; duplicate requests reuse one pending promise. A failed bundle keeps the camp usable, blocks combat and supports explicit retry. No hunt count or timer starts before readiness. Returning through another page or changing stage invalidates a pending launch intent; completed image downloads remain reusable.
- Preserve the gesture-time audio unlock before awaiting assets. Skip world rendering until the combat set and matching region are ready. Browser module query versions are updated for the new backup/inventory bounds.

## Measurements

- Required JS-managed cold-camp images: **22 → 3**, **37,350,676 → 4,474,690 bytes**, **88.02% less required transfer before camp readiness**. Theoretical decoded RGBA: **170,297,784 → 24,625,224 bytes**. These sizes exclude HTML/CSS artwork, fonts, DOM lazy thumbnails, cache, network time and GPU. The first forest hunt still needs the original total **37,350,676 bytes**; this change defers the remaining 32,875,986 bytes rather than recompressing images or claiming faster frame rates. All delivered image files are unchanged. Reproduce with tools/measure-loading084.mjs; loading.json.
- Matched nine initial uninterrupted automated runs have identical combat outcome, stage, level, kill count, time, item count and rarity histogram to 0.83. Automatic conversions fall **632 → 426** across the sample. First bag saturation shifts from **53.2–81.8s** to **118.1–146.4s** in eight paths; the ninth produces only 38 items and does not fill 48 slots before the first time-out. These are simulation seconds and selected seeds, not human playtime or a long-term economy survey. bag-comparison.json.
- With real earned equipment/point/forge preparation and checkpoint retries, **9/9 paths complete all three chapters**, as in 0.83. No injected campaign resources or invulnerability. Recovery/file backup agree and repeated return/reload never pays the same reservation twice. simulation.json; tools/measure-quality084.mjs.
- Density fixture: 32 living enemies, Node engine CPU P95 0.026ms, P99 0.072ms, 2397 warm samples. The stress fixture alone uses invulnerability; this is not Canvas/GPU/device FPS.
- Initial implementation with 48 static detail panels exhausted the Node VM integration process heap late in the full suite. The implementation was simplified to page 24 cells/panels, preserving the original bound on detailed inventory DOM rather than increasing the test heap. The integration host also releases each closed test tab's DOM, event handlers and Canvas recordings after the test, instead of retaining them across the entire VM suite. Static audit now finds **1512 unique IDs**, zero missing local HTML/CSS/module paths. Capacity is 48 while only 24 card/action IDs exist. This is structural evidence, not a measured browser heap reduction.

## Validation and limits

**613/613 full-suite checks and 19/19 focused integration checks passed.** Results are recorded in tools/reports/quality084-all-tests.txt and quality084-targeted.txt. New cases cover actual cold camp, deferred first launch, duplicate clicks, navigation cancellation, partial/late shared failure, retry without automatic start, preparation routes and 48th-item ownership/protection through paging, backup and reload. Existing capacity boundary fixtures now fill the actual 48-slot bound, while the old 24-slot profile remains a migration case.

The managed cloud environment has no Sites control-browser capability. Direct browser/device visual QA was therefore skipped; no preview server/browser was installed, no personal computer or login was used. Exact CSS pixels, phone font wrapping, touch feel, first-hunt network latency and actual browser/GPU memory remain unmeasured.
